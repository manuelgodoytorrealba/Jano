JANO — Agent Operating Guide
Product Vision

JANO is a premium platform for cultural discovery, connected knowledge and editorial exploration.

It combines the depth of a research library, the clarity of a museum exhibition and the discoverability of a modern graph-based knowledge system.

Users should never feel like they are navigating a database.

They should feel like they are exploring culture.

Everything built inside JANO must reinforce that vision.

Product Principles

JANO is not:

a CRUD application
a CMS with pages
another Google Arts clone
a digital encyclopedia
a bookmarking tool

JANO is:

a graph-native knowledge platform
an editorial discovery engine
a visual research environment
a personal cultural workspace
a premium reading experience

Knowledge is explored, not searched.

Relationships are first-class citizens.

Core Product Pillars

Every feature should strengthen at least one of these pillars.

Connected Knowledge
Visual Exploration
Editorial Storytelling
Personal Research
Intelligent Discovery
Premium Product Quality

If a feature strengthens none of them, reconsider building it.

From any artwork the user should naturally discover:

artists

Entity-First Architecture

Everything in JANO revolves around Entities.

Never design features around pages.

Pages are simply different ways of exploring entities.

Examples:

Graph Philosophy

The graph is not an optional visualization.

The graph is the navigation model.

Every relation should answer:

Why are these connected?

Connections must feel editorially meaningful.

Avoid meaningless autogenerated networks.

Quality beats quantity.

Editorial Thinking

Editors are creating knowledge, not filling forms.

Every interface should help answer:

Why does this entity matter?
How does it connect?
What should users discover next?
What stories emerge from these relationships?

The admin should feel closer to publishing software than database software.

calm

Responsive Strategy

The primary design target is desktop laptops.

Optimize first for widths between:

1100px — 1500px

This corresponds to the most common MacBook viewport used during development.

After this experience is polished:

scale upwards
then optimize tablets
finally mobile

Desktop quality always drives the system.

Never compromise desktop ergonomics to solve edge cases first.

Curated Experience

Curated pages are not lists.

They are guided exploration experiences.

Each curated page should combine:

editorial narrative
graph exploration
related entities
recommended continuations
contextual reading

The user should always know:

"I've understood this topic."

and simultaneously

"There's another interesting path I can follow."

Museums

Museums are exploration hubs.

A museum page should not simply list artworks.

It should expose multiple editorial entry points.

Examples:

Horror in the Prado
Religion in the Prado
Women Artists
Symbolism Route
Masterpieces in One Hour

Museums become gateways into the graph.

Search Philosophy

Search is the beginning of exploration.

Results should encourage discovery.

Prioritize:

grouped results
meaningful relationships
editorial recommendations
graph entry points
contextual navigation

Avoid infinite undifferentiated lists.

Source of Truth

Backend owns:

business rules
relation resolution
recommendation logic
entity integrity

Frontend owns:

presentation
interactions
local state
editing experience
previews

Never duplicate business logic.

Avoid dual-truth systems.

Architecture Principles

Prefer:

vertical slices
domain-driven naming
reusable UI
composable services
isolated presenters
cohesive modules

Avoid:

god components
shared utilities without ownership
hidden coupling
duplicated business rules
Frontend Standards

Every component should have one responsibility.

Split components before they become difficult to reason about.

Target:

readable templates
minimal inputs
explicit outputs
reusable primitives

Component style budget is mandatory.

Treat budget failures as architectural warnings.

Backend Standards

Services should own cohesive domain behavior.

Prefer explicit domain rules over heuristics.

Protect data integrity.

DTO boundaries are mandatory.

Schema changes should preserve compatibility whenever possible.

Refactoring Rules

Refactor when:

feature velocity decreases
files become difficult to understand
duplication appears
testing becomes harder
responsibilities blur

Do not refactor only for aesthetics.

Refactoring must improve maintainability.

Performance Philosophy

Optimize only after measuring.

Prioritize:

perceived performance
navigation smoothness
rendering stability
graph responsiveness
search latency

Avoid premature optimization.

Technical Debt Policy

Never hide technical debt.

If architecture is becoming difficult:

stop

identify the root cause

refactor

continue.

Small continuous refactors are preferred over massive rewrites.

Production Safety

Production deployments must use:

infra/docker-compose.prod.yml

through

infra/scripts/prod.sh

Never:

reset production databases
use db push in production
destroy volumes
bypass migration workflow

Backups are mandatory before schema changes.

Treat PostgreSQL and uploads as one deployment snapshot.

Communication

Challenge ideas respectfully.

If a proposal weakens the product, explain why.

Recommend better alternatives.

Think beyond the requested task.

Do not optimize only for today.

Optimize for the product JANO will become in three years.
